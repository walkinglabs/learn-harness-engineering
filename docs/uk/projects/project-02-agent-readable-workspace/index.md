# Проєкт 02. Зробіть проєкт зрозумілим і відновлюйте роботу з місця зупинки

## Що ви робите

Додайте «зрозумілість» до репозиторію, щоб новий агент міг швидко зрозуміти структуру проєкту, дізнатися поточний прогрес і продовжити роботу. Конкретно: реалізуйте імпорт документів, деталізований перегляд документа та локальну персистентність — протягом двох сесій.

Обидва прогони починаються з того самого коду зі `starter/`. У першому ви використовуєте мінімальний harness зі стартового каталогу, без `session-handoff.md`. У другому берете `AGENTS.md` з `solution/`, де є правила передачі роботи, і наприкінці сесії A створюєте `session-handoff.md`. Кожен прогін має дві сесії: друга підхоплює роботу, яку не завершила перша. За наведеним нижче порядком проведення код, промпт, агент і момент зупинки однакові. Так порівнюємо harness: правила в `AGENTS.md` разом із нотаткою для передачі роботи.

## Інструменти

- Claude Code або Codex
- Git
- Node.js + Electron

## Механізм harness

Простір роботи, зрозумілий агенту, + файли постійного стану

| Директорія | Що містить | Що порівнювати |

Продуктові функції: імпорт документів, повне завантаження деталей/вмісту документа та персистентність між перезапусками. Функція harness — простір роботи, зрозумілий для передачі між сесіями.

## Порядок проведення

Між двома прогонами може різнитися лише harness. Вихідний код, промпт, агент і момент зупинки сесії A залишаються однаковими. У сесії A реалізуйте імпорт документів та перегляд повного вмісту, у сесії B — збереження даних між перезапусками, як описано в [README проєкту](https://github.com/walkinglabs/learn-harness-engineering/blob/main/projects/project-02/README.md).

1. Підготуйте два ізольовані робочі каталоги, наприклад `p02-baseline/` і `p02-improved/`. Проводьте прогони по черзі: завершіть обидві сесії, заархівуйте результати, видаліть робочий каталог і лише тоді починайте інший прогін. Не розділяйте прогони гілками Git. Агент для програмування може читати інші гілки й сусідні каталоги. Якщо у слабкому прогоні він бачить файли із сильного, порівняння стає некоректним. Це те саме правило, що й у проєкті 01.
2. Скопіюйте [`projects/project-02/starter/`](https://github.com/walkinglabs/learn-harness-engineering/tree/main/projects/project-02/starter) як стартову точку для обох прогонів. Каталог підготовлено на основі рішення проєкту 01: функції першого проєкту вже проходять перевірки, а три функції проєкту 02 в `feature_list.json` позначено як `not-started`. Якщо хочете продовжити власний проєкт 01, візьміть той самий його знімок для обох прогонів. Головне, щоб вихідний код був ідентичний.
3. Використайте той самий промпт для обох прогонів, наприклад: «Реалізуй імпорт документів через діалог вибору файлу, детальний перегляд із завантаженням повного вмісту та збереження даних, щоб імпортовані документи не зникали після перезапуску застосунку».
4. Не копіюйте в жоден робочий каталог `solution/docs/`, `solution/feature_list.json` або `solution/session-handoff.md`. Там описано вже готові сценарії імпорту й отримання вмісту, а всі функції позначено як `pass`. Це видало б агенту готове рішення. В обох прогонах залиште `docs/ARCHITECTURE.md`, `docs/PRODUCT.md` та `feature_list.json` незмінними, як у `starter/`.

### Перший прогін (слабкий harness)

У `p02-baseline/` залиште стартовий harness без змін: короткий `AGENTS.md`, каталог `docs/` і `feature_list.json`, без `session-handoff.md`. Не видаляйте ці файли. Слабкий harness мінімальний, а не порожній.

**Сесія A:**

1. Запустіть агента з промптом завдання.
2. Самостійно зупиніть сесію, коли імпорт і детальний перегляд уже працюють, але збереження даних ще не реалізовано. Перевірте це так: відкрийте застосунок, імпортуйте файл `.txt` або `.md` через діалог вибору файлу, знайдіть його у списку й відкрийте, щоб переглянути повний вміст. Після перезапуску імпортований документ іще має зникати. Використайте той самий критерій для другого прогону.
3. Не просіть агента створювати нотатку для передачі роботи або файл із підсумками.

**Сесія B:**

1. Почніть нову сесію агента в тому самому каталозі й скажіть лише: «Продовжуй роботу».
2. Зафіксуйте час до першої змістовної зміни в коді й кожен випадок, коли агент заново з'ясовує те, що вже знав у сесії A: архітектуру, команди або яку функцію ще не завершено.

### Другий прогін (сильний harness)

Перед сесією A замініть `AGENTS.md` у `p02-improved/` на [`solution/AGENTS.md`](https://github.com/walkinglabs/learn-harness-engineering/blob/main/projects/project-02/solution/AGENTS.md). Він додає правила запуску, ієрархію документації, вимогу оновлювати документацію, критерій завершення з підтвердженням у `feature_list.json` та розділ про передачу роботи між сесіями. Більше нічого не змінюйте. У `AGENTS.md` є й інші правила, тому цей прогін перевіряє весь harness; різницю в сесії B не можна пояснити лише нотаткою. Щоб окремо виміряти вплив передачі роботи, додайте третій прогін: залиште стартовий `AGENTS.md` і додайте до нього лише розділ про передачу.

**Сесія A:**

1. Запустіть агента з тим самим промптом завдання.
2. Зупиніть його на тому самому етапі: імпорт і детальний перегляд працюють, а збереження даних після перезапуску ще немає.
3. Перед завершенням сесії попросіть агента створити в корені репозиторію `session-handoff.md` за [шаблоном передачі роботи](./../../resources/templates/session-handoff.md): що перевірено, що змінилося, що не працює або ще не перевірено і яким має бути наступний крок. [`solution/session-handoff.md`](https://github.com/walkinglabs/learn-harness-engineering/blob/main/projects/project-02/solution/session-handoff.md) — приклад для завершеного проєкту. Там усі функції вже готові, тож не копіюйте його.

**Сесія B:**

1. Почніть нову сесію агента в тому самому каталозі й скажіть лише: «Продовжуй роботу». Вказівка прочитати `session-handoff.md` міститься в `AGENTS.md`, а не у вашому промпті.
2. Запишіть ті самі показники, що й у першому прогоні.

## Як виміряти результати

| Показник | Опис |
|------|------|
| Час до поновлення роботи в сесії B | Від початку сесії до першої змістовної зміни в коді |
| Повторне з'ясування деталей | Скільки разів агент заново з'ясовує відомості про архітектуру, команди чи стан проєкту, які вже були відомі |
| Якість передачі | Чи нотатка повна, точна й придатна для подальшої роботи (лише другий прогін) |
| Повторна робота | Яку частку виконаного в сесії A агент переробив у сесії B |
| Підсумкова готовність | Чи реалізовано наприкінці всі три функції |

## Що здавати

- Для слабкого harness: записи діалогів або журнали сесій A і B
- Для сильного harness: ті самі матеріали, а також використаний `AGENTS.md` та створений агентом `session-handoff.md`
- Коротке порівняння швидкості поновлення роботи та якості відновлення контексту
