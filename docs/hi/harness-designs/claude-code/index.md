# Claude Code के हार्नेस डिज़ाइन का ब्रेकडाउन (Breaking Down Claude Code's Harness Design)

Anthropic अपने लेख [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) में साफ़ कहती है कि विश्वसनीयता मॉडल से नहीं, बल्कि हार्नेस से आती है, और एजेंट्स को मॉडल के बाहर के कड़े नियमों की ज़रूरत होती है। Claude Code इस विचार का एक प्रोडक्शन उदाहरण है; Anthropic खुद इसे एक **एजेंटिक हार्नेस (agentic harness)** के रूप में वर्गीकृत करती है। Claude Code आज का सबसे गहराई से जाँचा-परखा सार्वजनिक हार्नेस है: यह लेयर्ड मेमोरी, कॉन्टेक्स्ट कॉम्पैक्शन, परमिशन्स, हुक्स, सब-एजेंट्स, और सेशन निरंतरता जैसे कोर्स के लगभग हर मुख्य मैकेनिज्म को एक संपूर्ण प्रोडक्ट में बदलता है।

## एक वाक्य में सारांश (In One Sentence)

Claude Code के मूल में एक सरल `while` लूप है: मॉडल को कॉल करो, टूल चलाओ, रिज़ल्ट देखो, और फिर से मॉडल को कॉल करो। लेकिन **इसका अधिकांश कोड उस लूप में नहीं है; बल्कि वह लूप के चारों ओर बने सबसिस्टम्स में है** — परमिशन सिस्टम, कॉन्टेक्स्ट कॉम्पैक्शन पाइपलाइन, एक्सटेंशन मैकेनिज्म, सब-एजेंट ऑर्केस्ट्रेशन, और सेशन स्टोरेज। यही हार्नेस का सार है: लूप तो सिर्फ कंकाल है, लेकिन विश्वसनीयता कंकाल के चारों ओर की इंजीनियरिंग तय करती है।

## निर्देश सबसिस्टम: लेयर्ड मेमोरी सिस्टम (Instruction Subsystem)

Claude Code का मेमोरी सिस्टम हार्नेस थ्योरी में इसका सबसे बड़ा योगदान है। आधिकारिक दस्तावेज़ [How Claude remembers your project](https://code.claude.com/docs/en/memory) स्पष्ट करता है कि हर नया सेशन एक खाली कॉन्टेक्स्ट विंडो से शुरू होता है और दो मैकेनिज्म्स के ज़रिए ज्ञान को आगे बढ़ाता है: `CLAUDE.md` फाइल्स (जो आप लिखते हैं) और ऑटो मेमोरी (जो नोट्स Claude खुद लिखता है)।

दायरे के हिसाब से `CLAUDE.md` फाइल्स 4 श्रेणियों में बँटी हैं:
- **Organization policy level**: कंपनी-स्तरीय मानकों के लिए (जैसे `/etc/claude-code/CLAUDE.md`)।
- **User-level `~/.claude/CLAUDE.md`**: व्यक्तिगत प्राथमिकताएँ जो सभी प्रोजेक्ट्स पर लागू होती हैं।
- **Project-level `./CLAUDE.md`**: आर्किटेक्चर, टेक स्टैक, और वेरिफिकेशन कमांड्स का सिस्टम-ऑफ-रिकॉर्ड।
- **Local-level `./CLAUDE.local.md`**: प्रोजेक्ट के अंदर व्यक्तिगत प्राथमिकताएँ जो गिट में कमिट नहीं होतीं।

इसके अलावा दो और मैकेनिज्म्स हैं:
- **सबडायरेक्टरी स्तर पर ऑन-डिमांड लोडिंग**: सबडायरेक्टरीज़ की फाइल्स तभी लोड होती हैं जब Claude उस डायरेक्टरी की फाइल्स को पढ़ता है।
- **Auto memory**: आपके सुधारों के आधार पर Claude खुद नोट्स लिखता है (प्रति सेशन अधिकतम 200 लाइन्स या 25KB लोड होती हैं)।

यह पदानुक्रम लेक्चर 4 ("एक ही बड़ी निर्देश फ़ाइल क्यों फेल होती है") का व्यावहारिक जवाब है।

## कॉन्टेक्स्ट सबसिस्टम: पाँच परतों वाली कॉम्पैक्शन पाइपलाइन (Context Subsystem)

Claude Code केवल "भर जाने पर समरी बनाने" के बजाय एक **पाँच-लेयर कॉम्पैक्शन पाइपलाइन** का उपयोग करता है: पहले दोषरहित प्रूनिंग (अनावश्यक टूल आउटपुट हटाना), फिर स्ट्रक्चर्ड डिस्टिलेशन, और उसके बाद ही LLM समरी, जिसमें अत्यधिक कॉम्पैक्शन को रोकने के लिए सर्किट ब्रेकर्स लगे होते हैं।

इसके साथ **अपेंड-ओरिएंटेड सेशन स्टोरेज** (`history.jsonl`) जुड़ा है, जो `/resume` और ब्रांचिंग की सुविधा देता है। यह सुनिश्चित करता है कि "हर सेशन एक अच्छा हैंडऑफ छोड़े।"

## टूल सबसिस्टम: चार एक्सटेंशन मैकेनिज्म (Tool Subsystem)

Claude Code अपने एक्सटेंशन इंटरफ़ेस को चार श्रेणियों में बाँटता है:
- **Skills**: `SKILL.md` द्वारा परिभाषित प्रक्रियात्मक ज्ञान, जो प्रोग्रेसिव डिस्क्लोज़र के ज़रिए ज़रूरत पड़ने पर लोड होता है।
- **MCP**: JSON-RPC प्रोटोकॉल जो बाहरी सिस्टम्स और टूल्स से कनेक्ट करता है।
- **Hooks**: लाइफसाइकिल इवेंट्स (`PreToolUse`, `PostToolUse`, `Stop`) से जुड़ी निश्चित स्क्रिप्ट्स।
- **Subagents**: जटिल टास्क्स को समर्पित स्पेशलाइज़्ड एजेंट्स को सौंपना।

महत्वपूर्ण डिज़ाइन **ज़िम्मेदारियों का अलगाव** है: `CLAUDE.md` "क्या" संभालता है, Skills "कैसे" संभालती हैं, MCP "कहाँ कनेक्ट करना है" संभालता है, और Hooks "कब लागू करना है" संभालते हैं।

## फीडबैक और सत्यापन: निश्चित सीमाएँ + मानवीय-एजेंट सहयोग (Feedback and Verification)

- **परमिशन सिस्टम**: कम जोखिम वाले ऑपरेशन्स अपने-आप चलने दिए जाते हैं, जबकि उच्च जोखिम वाले ऑपरेशन्स नीति के अनुसार रोक दिए जाते हैं या पुष्टि माँगी जाती है। यह लेक्चर 7 के "टास्क सीमाएँ तय करने" को कोड में बदलता है।
- **ह्यूमन-इन-द-लूप नियंत्रण**: एजेंट को अनियंत्रित भटकने से रोकने के लिए रनटाइम पर मानव डेवलपर का हस्तक्षेप संभव रहता है।

## अपनाने लायक डिज़ाइन्स (Designs Worth Adopting)

1. **निर्देशों को पदानुक्रम में बाँटें**: ऑर्गनाइज़ेशन, यूज़र, प्रोजेक्ट, और सबडायरेक्टरी के स्तर पर अलग-अलग नियम रखें।
2. **मल्टी-स्टेज कॉम्पैक्शन का उपयोग करें**: सीधे समरी बनाने से पहले अनावश्यक टूल डेटा और डुप्लिकेट्स को फ़िल्टर करें।
3. **ज़िम्मेदारियों को अलग रखें**: `CLAUDE.md` (नियम), Skills (तरीका), और MCP (टूल्स) को आपस में न मिलाएँ।
4. **सेशन हिस्ट्री को रीप्ले-योग्य बनाएँ**: अपेंड-ओन्ली लॉग्स रखें ताकि पुराने सेशन्स को आसानी से दोबारा शुरू किया जा सके।
